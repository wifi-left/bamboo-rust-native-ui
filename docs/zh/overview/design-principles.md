# 设计原则

> 框架所围绕的契约，以及它与即时模式 UI 相比的代价。

## 契约

这些规则位于 crate 根文档（`crates/native-ui/src/lib.rs`）和 README 中。它们不是指导原则；每个模块都应遵循它们。

### 应用计算控件矩形

没有测量过程，也没有约束求解器。应用为每个控件分配一个矩形，通常在 `Host::resize` 中，框架永远不会自行更改它（应用某个布局时，布局文档可能会改它）。控件的首选高度只存在于可选的垂直堆叠辅助函数中；它不参与页面布局。

结果：布局确定且廉价。一次尺寸改变只跑一遍应用的算术，设置新矩形，然后使窗口失效。

### 框架只绘制脏矩形

状态变化永远不会触发重新布局或全窗口重绘。容器将变化控件的矩形记录为损坏，宿主将损坏合并为一小组独立片段，并且只重绘与它们相交的控件。

结果：对两个小控件的悬停只耗费两次小重绘，即使它们在页面上相隔很远。脏片段在合并为边界框之前最多保持 32 个独立片段。

### 每个窗口一个持久后台缓冲

每个窗口在其生命周期内拥有一个后台缓冲。绘制会画入该缓冲；控件绘制完成后，只有脏片段被复制到窗口。因此，一个控件可以绘制其整个矩形，即使只有一个角发生了变化：缓冲中未被触及的像素仍然是正确的。

结果：不必推理控件的部分状态，也没有闪烁，代价是每个窗口一个全窗口大小的表面。

### 绘制路径上不分配内存

脏矩形是借用的（`ctx.dirty`），文本是借用的，画刷、字体、转换后的图像和抗锯齿掩码都在后端中按窗口生命周期缓存。控件绘制代码不得分配内存；如果需要临时值，就存到控件或容器上。

结果：绘制开销是稳定的，不依赖于分配器的行为。该规则还意味着控件不得每帧为绘制的文本构建一个 `String`。

### 空闲即零绘制

没有周期性重绘。窗口在有东西使其失效时才会绘制（输入、程序化更改、尺寸改变或显式的动画定时器）。想要动画的应用使用 `WindowHandle::set_animation_timer` 安装一个定时器，并从 `Host::timer` 使动画区域失效。

结果：空闲窗口不消耗任何用于绘制的 CPU。每秒更新一次的进度条每秒只造成一次绘制，而不是六十次。

### 公共类型平台中立，宿主边界仅限 Windows

`Rect`、`Size`、`Point`、`Color`、`Event`、`KeyCode`、`Palette`、`WidgetId`、`Canvas` 和 `Painter` 都是普通的 Rust 类型。GDI/Direct2D 后端和窗口宿主位于 `#[cfg(windows)]` 之后；`Host`、`PaintCtx`、`WindowBuilder` 和 `WindowHandle` 仅在 Windows 上导出。只有平台层触及 `windows` crate。

结果：控件代码和测试可以在没有窗口的情况下编译，未来的后端可以在不更改调用点的情况下添加。

## 职责划分

| 问题 | 由谁回答 |
|---|---|
| 控件在哪里？ | 应用（`ui.set_rect`）或所应用的布局文档 |
| 它看起来是什么样？ | 控件（`Widget::paint`） |
| 指针是否在其上、是否被按下、是否拥有焦点？ | `Ui`（状态作为 `WidgetState` 传递） |
| 哪些控件是脏的？ | `Ui` 记录损坏；宿主合并它 |
| 窗口何时重绘？ | 宿主，在失效后由 `WM_PAINT` 触发 |
| 一次点击意味着什么？ | 控件（`Widget::input` 返回 `Option<M>`） |

控件永远不会直接使窗口失效：它从 `input` 返回一条消息，由应用决定什么发生了变化、要让哪个矩形受损。应用在每次回调中调用一次 `ui.flush_damage(window)`，因此一个事件中的所有变化变成一次重绘请求。

## 相对即时模式的权衡

即时模式库（egui 之流）每帧重建 UI 描述。Bamboo Native UI 保持控件存活并重绘变化。代价和收益彼此互为镜像。

| 关注点 | 即时模式 | Bamboo Native UI |
|---|---|---|
| 空闲开销 | 每帧一次完整重新布局和重绘 | 在某个东西使其失效之前零绘制 |
| 小变化的开销 | 整个窗口 | 仅脏片段 |
| 布局 | 灵活，带测量过程 | 应用计算矩形；无测量过程 |
| 状态 | 通常捕获在帧闭包中 | 存在于保留控件和应用结构体上 |
| 动画 | 免费，因为每帧都重绘 | 显式：安装定时器并使失效 |
| 控件身份 | 每帧重建 | 稳定的 `WidgetId`，焦点、无障碍和输入法依赖它 |
| 编写控件 | 绘制代码加布局提示 | `paint` 加 `input`，交互状态由容器拥有 |
| 尺寸改变 | 自动重新布局 | 应用必须在 `resize` 中重新计算矩形 |
| 部分重绘正确性 | 不适用 | 控件必须只在其矩形内绘制 |

保留模式要求的主要纪律是失效：在控件的 `input` 路径之外更改状态后，应用必须记录损坏（通常通过调用 `Ui` setter 然后调用 `flush_damage`）。它带来的主要回报是：没有东西变化时什么都不会发生，而这正是桌面应用的常态。

## 对控件作者的影响

- 只在 `rect` 内绘制。容器只 blit 控件的脏矩形，别的什么都不做，因此在其外部绘制要么被裁剪，要么永远不会被复制。
- 不要在 `paint` 中分配内存。复用控件上的缓存数据，或从 `WidgetPaint`（`text`、`images`、`palette`）借用。
- 不要指望矩形外的像素是最新的。另一个控件可能已独立重绘了它自己的区域。
- 从 `input` 返回消息；不要修改其他控件。应用决定一条消息意味着什么以及要使哪些矩形受损。
- 从 `WidgetState`（`hovered`、`pressed`、`focused`、`enabled`、`editing`、`caret_on`）读取交互状态，而不是自己跟踪它。
